# 0029. A worker resets its context by a handoff at a checkpoint, not by compaction

Date: 2026-09-21
Status: accepted

## Context
A worker session runs one issue from reading it to the merge, and its context only grows: the issue, the implementation, five reviewer reports per round, the pull request, CI logs, review comments. The sessions measured for [ADR 0017](0017-worker-subagents-run-in-the-foreground.md) reached 412k tokens. What a long context costs is not only money: the model's attention over it thins out, the early instructions compete with a transcript of dead ends, and the last stages of the pipeline — the ones that decide what gets merged — run in the worst context of the run.

Claude Code's own answer is auto-compaction: at the window limit it summarises the transcript and carries on. That keeps the shape of the session but loses control of what survives, at a moment nobody chooses, and the summary is a summary of everything, including the dead ends. It is a safety net, not a plan.

The pipeline has a better answer available to it, because its state is not in the transcript. The branch carries the work, GitHub carries the issue and the pull request, and this worktree's git directory carries the facts a stage hands to the next one ([ADR 0018](0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). What a fresh context would miss is only what the previous one decided and rejected on the way — which fits in a page. A spike on Claude Code 2.1.278 showed the mechanism: `/clear` sent into the pane fires the SessionStart hook with source `clear` and a new session id, the context is empty, and the process keeps running with its flags, its settings and its plugins.

## Decision
A worker hands its pipeline over to a fresh context in the same pane at a stage boundary, and never compacts on purpose.

The driver checks the context at two checkpoints: after the implementation stage, before the review stage, and after the pull request stage, before the CI stage. Both are boundaries at which everything the next context needs is already in git, in GitHub or in a record of this worktree — a stage is never handed over in the middle. `checkpoint.sh` answers with the reading of the pane's status line (ADR 0020); on `handoff: yes` the worker hands over, on `no` or `unavailable` it carries on as before.

Handing over means writing a note and letting a script do the rest. The note has four sections — decisions and why, rejected approaches, verified, open points and known limits — and `handoff.sh` refuses one that leaves any of them out, as it refuses a dirty working tree: the next context reads the branch, not a tree it cannot see. The script appends the base, the commits and the diffstat itself, so the note carries no fact a command can answer. It is written to this worktree's git directory, outside the tree and never committed, and it is the pipeline's own record: the pull request and the review summary are not copied into it, because at the second checkpoint both already have a place on disk and in GitHub.

The clearing is done by a detached process, because a session cannot clear itself from inside a turn. `handoff-resume.sh` waits until the pane's turn settles, sends `/clear` — but only into the session that asked for the handover and only once its turn has ended, never into a pane that has moved on, that waits on a dialog or that is still working. Everything it sends is keystrokes carrying an Enter, so the pane's state is read immediately before each of them and never once for all of them: between two prompts a minute passes, and the prompt before may be what opened the dialog the next would answer. The driver command then follows two signals and no guess: the pane reports an agent session id other than the one recorded at the handoff, so a fresh context exists, and the record is marked as injected, so that context has the note. Without the first the process sends a second `/clear` and then raises a Herdr notification for the maintainer, and never sends the driver command into the old context; without the second it raises one too, because a fresh context that was never given the note would take the driver command for the start of the issue and implement a branch that already carries the work. A record already marked as injected ends the handover the same way: the note is in a context this handover did not start, so clearing again would throw it away and driving the pane would resume the stage in the context that asked to be replaced.

In the new session the worker's SessionStart hook injects the full issue context again, the note — indented like the issue body and the comments above it, and framed as the report of a context that had read them, so it is read as data and no more able to imitate the framing around it than the issue text is — and the stage to resume at, exactly once: it marks the record before it emits, so a resume or a second handoff that never arrived injects nothing from it, and a mark it fails to write stops the injection rather than going ahead without the guard, and it passes over a record that names the session it is starting, so an auto-compact in the context that wrote the note cannot consume the note meant for its successor. `facts.sh` then prints `resume_stage:`, and the driver starts at that stage after reading the commit log and the diffstat instead of at stage 1. The note reaches no reviewer and no pull request author: their briefs are built from the diff, the gate record and the panel record, and a fresh reviewer that read the previous context's reasoning would no longer be the independent reader [ADR 0004](0004-reviewers-as-fresh-read-only-subagents.md) asks for.

The threshold stays `WF_HANDOFF_TOKENS` (default 120 000), under the `autoCompactWindow: 200000` a claim sets, so the handoff happens well before the safety net.

## Consequences
The review stage and the CI stage run in a context that holds the issue, a page of notes and the diff, instead of one that holds everything that happened before them. The work itself is never at risk in a handover: it is committed before the note is written, and the note is a page beside it.

What is at risk is judgement the note leaves out. The four sections are the pipeline's answer to that, and a fresh context that finds a gap has the branch, the issue and the records to fall back on — it re-reads rather than guesses. A note that is wrong is worse than one that is short, which is why the script appends every fact it can derive instead of asking the author to copy it.

The handover is the one moment in the pipeline where the agent's own continuation depends on a pane command. It can fail: a pane blocked on a permission dialog is never typed into, because the Enter of a `/clear` would answer a question the maintainer has not read, and a `/clear` can be swallowed. That is why the confirmation is the session id and not the sending of the keys, why there is a second attempt, and why the failure ends in a notification with the note still on disk — a maintainer can always clear the pane by hand and send `/worker:work`. Outside a Herdr pane there is no pane to clear at all: `checkpoint.sh` answers `unavailable` there and the worker carries on, so a session started by hand and a worker in the Docker sandbox behave as they did before this decision.

Two contexts now write into one worktree, one after the other. They never run at the same time — the old session has ended its turn before `/clear` and is gone after it — but the records they share are per worktree and not per session, so a handoff that stalls leaves a note that the next session started in that worktree will read. The note names its stage and its commit, and the pipeline is idempotent at a stage boundary, so the cost of reading it late is a re-run of a stage, not a wrong merge. One stage needed a guard of its own for that to hold: a resume at the ci stage skips the review, which every run used to pass through, so `panel.sh verdict` — the one word the unattended finish gates on — now reads `draft` for a summary recorded before the current head ([ADR 0018](0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). A skipped review can leave a stale record; it can no longer let a merge through.

The pane's status line writes a context size per worktree, not per session (ADR 0020), so for a few seconds after a handover the value describes the context that is gone. The first checkpoint of the fresh context comes stages later, long after its own first render, so nothing reads that window; a threshold under 120k would be the case to revisit it in.
