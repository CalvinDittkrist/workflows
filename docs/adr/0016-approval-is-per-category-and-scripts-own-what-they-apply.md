# 0016. Approval is per category, and scripts own what they apply

Date: 2026-09-20
Status: accepted

## Context
The findings report printed every finding of a category under one heading, `the run performs`, so a reader concluded that each line was an item they had approved and that nothing else would happen (#15, a follow-up of #3). That is true of `delete` and `issue` findings, which the scripts execute one by one, and of `replace` and `create` findings, which `cleanup.sh` turns into `todo:` lines the agent works through. It is not true of `configure`: `workspace.sh --apply` applies the whole difference it computes itself, so a single `configure` line drives nothing. It is also not the whole story for a scaffolded category, because `scaffold.sh` creates every baseline file of it that is missing, listed or not. The audit and the apply phase are separated by a pull request and its merge, so the workspace difference the maintainer read can no longer be the one that is applied.

## Decision
Approval stays per category: one answer, `approve` or `reject`, for all findings of a category, and a rejected category is left untouched. The report groups the findings of a category by action instead of listing them under one heading. `delete`, `replace` and `create` are the lines the run works through one by one; `configure` lines are what `workspace.sh` found at the audit, and approving the category applies the whole difference, recomputed after the cleanup pull request is merged. For every category `scaffold.sh` has templates for (`agent-config`, `docs`, `tests-ci`, `workspace`) the report says that approving it creates every baseline file of the category that is missing, whether a finding lists it or not; the other categories are not scaffolded and get no such line. Approving `agent-config` also brings `.claude/settings.json` to the template, which the report says too, because `scaffold.sh` writes that file whether it exists or not. A scaffolded category without findings cannot be answered at all and is scaffolded for the same reason, so the report names it in one line of its own.

`finalize.sh` compares the settings `workspace.sh --apply` changed with the `configure` findings the report recorded and prints one line naming the settings it changed without a finding and the audited ones that were already at the standard. The settings the apply phase of a run has worked on are kept in `<git dir>/standardize/workspace-handled`, so a second `finalize.sh` does not report what the first one brought to the standard; `report.sh` clears that record with the approvals. The line informs; it never skips a change and never aborts the run.

## Consequences
The report says what the unit of decision is, so approving a category is an informed decision, and a category that is not scaffolded and has no `configure` finding still promises nothing beyond its lines. What the apply phase applies is untouched, so a scaffolded category without findings is still scaffolded without being asked about; the report now says so instead of hiding it. The apply phase is unchanged, which keeps the scripts idempotent and keeps one source of truth for the workspace: the difference the script computes when it runs, never a list recorded hours earlier. A maintainer who objects to a single setting has to reject the whole category and change that setting by hand. The scaffolded categories now live in `WF_SCAFFOLD_CATEGORIES` in `lib.sh` next to the `put` calls in `scaffold.sh` that define them, and a test scaffolds with all of them skipped to catch the two drifting apart.

Rejected: per-finding approval of `configure` lines, with an exclusion parameter in `workspace.sh`. A setting left out of the standard that way is reported as drift by `check.sh` on every later run, which turns a one-time decision into a permanent warning, and it would make the applied state depend on a stored list instead of the standard. Also rejected: letting `finalize.sh` refuse or stop when the applied difference deviates from the audit. The deviation is normal — the merge of the cleanup pull request itself changes the workspace — and a run that has already deleted files and opened issues must finish.
