# Architecture

## Purpose
This repository packages an opinionated way of working with coding agents as Claude Code plugins. It optimises for throughput (many issues in parallel), token economy (each agent sees only what its job needs), consistency (every issue goes through the same gates) and safety (isolation per issue, read-only reviewers, no silent merges).

## Components
| Component | Responsibility | Entry point |
| --- | --- | --- |
| `orchestrator` plugin | One session per repository that opens planning sessions, assigns issues to worktrees and merges finished PRs. Coordination only. | `claude --agent orchestrator`; `plugins/orchestrator/scripts/*.sh` |
| `planner` plugin | One session per topic. Turns an idea or an issue into agent-ready issues: question rounds, spec, tickets with blocking edges, triage, research, prototypes. Accepts a finished spec against the code and closes it. Writes issues, never code. | SessionStart hook + `/planner:plan`; `plugins/planner/scripts/*.sh` |
| `worker` plugin | One session per issue. Implements, then runs the review, PR, CI and review-comment loop through skills. | SessionStart hook + `/worker:work`; `plugins/worker/scripts/*.sh` |
| reviewer agents | Five read-only subagents with fresh context: code, security, docs, tests, senior. Report findings in a fixed format. | `plugins/worker/agents/*-reviewer.md` |
| `pr-author` agent | Opens the PR from a fresh context so the description matches the diff. | `plugins/worker/skills/pr` (forked skill) |
| `spec-checker` agent | Read-only subagent with a fresh context that judges every checkable statement of a spec against the code during an acceptance. | `plugins/planner/agents/spec-checker.md` |
| `factory` service | One service on a host of its own that works the issues routed to it unattended, as a second driver over the same worker pipeline, and serves what it did over a read-only HTTP interface. A Go binary, not a plugin ([ADR 0020](adr/0020-the-factory-is-a-second-driver-over-the-worker-pipeline.md)). Today it runs in fake mode only. | `factory/`; `go -C factory run . -fake -config factory.json` |
| `repo-standards` plugin | Owns the [repository standard](repo-standard.md): audits a repository against it, applies the approved findings through a backup tag, a cleanup pull request and issues, scaffolds the baseline (`AGENTS.md`, the `CLAUDE.md` import, a `Makefile` with `check`, docs, settings) and checks it, including stray agent configuration; brings the GitHub workspace to the standard with a dry-run-first script. | `/repo-standards:standardize`, `/repo-standards:apply`, `plugins/repo-standards/scripts/check.sh`, `workspace.sh` |
| auditor agents | Six read-only subagents with fresh context, one area each: files, agent configuration, docs, tests and CI, GitHub workspace, security. Return findings in a fixed format. | `plugins/repo-standards/agents/*-auditor.md` |
| Herdr | Terminal workspace manager: one workspace per worktree, agent lifecycle detection, notifications. | `herdr worktree|agent|workspace` |
| GitHub | Issues are the unit of work, PRs the unit of delivery, CI (the job `check` running `make check`) and Codex review the external gates. | `gh` (or `npx gh-axi`) |
| Docker Sandboxes (optional) | Container per worktree for workers that should not touch the host. | `plugins/orchestrator/scripts/sbx-worker.sh` |

## Data flow
0. `/orchestrator:plan <idea | #N>` → `plan.sh` creates `plan/<slug>` (topic or issue in the branch description), a worktree and workspace, starts `claude --agent planner` with `/planner:plan`. The planner grills, writes a `spec` issue, cuts it into `ready-for-agent` sub-issues with native blocking edges and an optional milestone (`issue.sh`), or triages an existing issue into an agent brief. `/planner:finish` removes the worktree; the plan branch never carries commits. `board.sh` then lists the frontier with each issue's milestone: agent-ready issues with no open blocker, no assignee and no worktree, and after it the specs ready for acceptance: open `spec` issues with native sub-issues and none of them open, with the command that opens a planning session on one. Both sections are derived from GitHub on every run and keep no state. `/planner:accept [spec]` runs the acceptance in that planning session: `accept-facts.sh` prints the facts it works from (the spec with its milestone, each ticket with its state and the merged pull requests that closed it, the union of the files those changed, and the deviations accepted in earlier runs), and refuses a worktree that is behind the base branch, because the checker judges the code that worktree carries; one read-only `spec-checker` with a fresh context then judges every checkable statement of the spec against that code and answers `item:` lines, and `accept-report.sh` counts them per section and verdict, refuses a malformed line and names a checkable section the checker left out. The maintainer decides per item that is not met: a gap ticket (a `ready-for-agent` sub-issue on the spec's milestone), an accepted deviation (a comment on the spec that opens with the marker line, which a later run skips) or no finding. Gap tickets keep the spec open until they close and the acceptance has run again; with nothing left open, `accept-close.sh` closes the spec as completed with the closing comment and refuses while a sub-issue is open ([ADR 0015](adr/0015-a-spec-with-tickets-is-closed-by-an-acceptance.md)).
1. `/orchestrator:claim N` → `claim.sh` reads the issue, refuses it unless it carries `ready-for-agent` (the error names its labels and the fix; `--force` is the exception, [ADR 0014](adr/0014-claims-require-ready-for-agent.md)), derives `<type>/<N>-<slug>`, creates `<repo>/.claude/worktrees/<branch>` through Herdr (new workspace and pane), starts `claude --agent worker` there with `--settings '{"env":{"WF_MODE":…,"WF_ISSUE":N,"CLAUDE_CODE_DISABLE_BACKGROUND_TASKS":"1"}}'` and the initial prompt `/worker:work`. The background switch makes the session's subagents block and return their report as the tool result, so the worker never spends turns waiting for them ([ADR 0017](adr/0017-worker-subagents-run-in-the-foreground.md)); planning sessions keep background subagents for their research stage.
2. Worker SessionStart hook: parses the issue number from the branch, assigns the issue to the current GitHub user, injects title, body, labels and recent comments as context, marked as untrusted data.
3. `/worker:work` implements and verifies in the worker's own context, then `/worker:review` launches the reviewer panel in parallel, in one message (fresh contexts, read-only). The worker verifies with `gate.sh run`, which runs the gate once, records the result for the current head in this worktree's git directory and writes the output to a file beside it, printing it only when the gate failed; `gate.sh print` turns that record into the gate block of a brief and answers for the current head or not at all, so a record from an older commit or from a dirty working tree reads as none instead of as an older value. Every round runs the gate once, after its fixes are committed and before the launch, launches no reviewer on a failed gate, and copies that block into every reviewer's brief: no reviewer runs the gate itself ([ADR 0019](adr/0019-the-gate-runs-once-per-review-round.md)). The reports arrive as the results of those calls; the worker fixes findings and re-reviews until PASS or the round limit.
4. The review stage ends with `panel.sh record`, which stores the panel summary, the commit it describes and the draft verdict derived from it in this worktree's git directory, and refuses a block without a parseable `panel:` line. `/worker:pr` forks into `pr-author`, whose brief is the diff context plus `panel.sh print` and `gate.sh print`, so the panel result and the gate result reach the pull request body verbatim without the agent passing them by hand and without the author verifying anything itself; a panel that did not pass opens a draft only the maintainer lifts, and with nothing recorded the body says the panel result is unknown ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). `pr-author` pushes and opens the PR. `/worker:ci` calls `pr-wait.sh`, which polls checks and waits for the configured bot reviewers, reporting a draft instead of waiting for a review no bot writes on one; `/worker:address-reviews` fixes unresolved threads and resolves them with a reply.
5. Manual mode: the worker reports `ready:`; the user runs `/orchestrator:merge PR`, which verifies mergeability, removes the workspace and worktree first, then squash-merges and deletes the branch. Yolo mode: `finish.sh` merges and a detached `cleanup-self.sh` removes the worktree; it merges only when the recorded panel says ready and the pull request is no draft, so a run whose panel did not pass ends with the maintainer instead.
6. Standardisation (per repository, user-invoked): `/repo-standards:standardize` in the target repository injects `facts.sh`, runs `workspace.sh` as a dry run, and launches the six auditors in parallel with the facts; the workspace auditor gets the dry-run output instead of exploring GitHub. `report.sh` merges their `finding:` lines into one report per category, separating what the run works through as listed from what `workspace.sh` decides for itself and from what becomes an issue, and `approve.sh` records the answer per category in `<git dir>/standardize/` ([ADR 0016](adr/0016-approval-is-per-category-and-scripts-own-what-they-apply.md)). Nothing changes in the repository or on GitHub. `/repo-standards:apply` then runs `backup.sh` (the protected tag `pre-standard` and the `skill-candidate` catalogue issue) and `cleanup.sh prepare` (worktree on `chore/standardize`, approved deletions, `scaffold.sh`). The agent fills in what needs judgement, and `cleanup.sh open` opens the cleanup pull request. `issues.sh` turns issue findings into `ready-for-agent` issues. After the merge, `finalize.sh` runs `workspace.sh --apply`, names where the applied difference deviates from the audited one, posts the snapshot to the catalogue issue and ends with `check.sh` ([ADR 0010](adr/0010-standardisation-audits-read-only-and-backs-up-before-deleting.md)).
7. Factory (unattended, on a host of its own): the service in `factory/` derives one queue of routed issues across its connected repositories, works them one at a time, and starts for each the session a local claim starts, headless and in a process group of its own. It reads the run from the worker's stream — stages from the `Skill` calls, a subagent's events from their `parent_tool_use_id`, the outcome from the final report, totals from the result line — and writes one JSON record and one append-only JSONL event log per run into its data directory. Its HTTP interface is read-only (`/api/status`, `/api/repositories`, `/api/line`, `/api/runs/{id}`): the factory is steered on GitHub alone ([ADR 0021](adr/0021-github-is-the-only-control-surface-of-the-factory.md)). It listens before it starts a run, so a second factory on the host fails before it takes an issue. So far only fake mode exists, with a canned queue and a scripted worker (`factory scripted-worker`) that needs no tokens, no git and no GitHub; the remote claim ([ADR 0022](adr/0022-a-claim-is-the-creation-of-the-branch-through-the-api.md)), the queue order ([ADR 0023](adr/0023-one-queue-one-worker-work-in-progress-first.md)), resume and cleanup ([ADR 0024](adr/0024-the-factory-never-deletes-work-on-its-own.md)), the host boundary ([ADR 0025](adr/0025-the-factorys-isolation-boundary-is-the-host.md)) and the quota check ([ADR 0026](adr/0026-the-quota-check-is-a-courtesy-not-a-guard.md)) are decided and arrive with their tickets.
8. Release (manual only): tickets carry a `vX.Y.Z` milestone from `/planner:tickets`, and their spec is attached to it too, so the release waits for its acceptance. `/orchestrator:release vX.Y.Z` → `release.sh` refuses while the milestone is missing or has open issues, or the tag exists. When the default branch is `dev` (`dev` plus `main`) it opens or finds the promotion PR `chore(release): vX.Y.Z` and waits until `merge.sh` merges it with a merge commit, then tags that commit. With `main` alone it tags the head of `main`. It publishes the GitHub release with generated notes and closes the milestone ([ADR 0012](adr/0012-releases-are-manual-and-close-a-milestone.md), [ADR 0013](adr/0013-promotions-merge-with-a-merge-commit-and-releases-tag-it.md)).

## Boundaries and constraints
- Scripts do, agents decide. Everything deterministic (GitHub calls, worktree lifecycle, polling, thread resolution) is a shell script with a stable text output; skills are short prompts around them. This keeps behaviour testable and token use low.
- Plugins are self-contained; they share no code at runtime. `lib.sh` is duplicated deliberately.
- The branch name is the state contract between orchestrator and worker (`<type>/<issue>-<slug>`) or planner (`plan/<slug>`, topic or issue in the git branch description). Everything else is re-derived from git and GitHub, so a crashed session can be resumed or re-claimed; the one exception is a fact of the running pipeline that exists nowhere else, such as the panel summary or the gate result, which a worker script leaves in this worktree's git directory and whose loss degrades the next stage instead of breaking it ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)).
- Reviewers and auditors never edit, and no reviewer runs the gate: it runs once per round in the worker's context and reaches them as a fact ([ADR 0019](adr/0019-the-gate-runs-once-per-review-round.md)). The worker never merges in manual mode. The orchestrator never edits code. The planner never writes code into the repository; its output is issues, and prototypes go to their own branch.
- Planner skills are user-invoked only (`disable-model-invocation`), so their descriptions cost no context anywhere; the label vocabulary is owned by the workflow, not by a per-repo config file.
- A worker never waits by sleeping or polling: its subagents run in the foreground, and a longer wait is one blocking script call that is run again (`pr-wait.sh`) ([ADR 0017](adr/0017-worker-subagents-run-in-the-foreground.md)). Planning sessions keep background subagents, because their research stage works while one runs.
- A worker works with the file tools, not the shell: a main-thread agent replaces the default system prompt, so its own prompt carries that guidance ([token budget](token-budget.md)). `scripts/context-report.py` measures it over finished sessions; it is a maintainer diagnostic over an internal transcript format, outside the plugins and never an input to the pipeline (Python, because the input is JSONL).
- Text from issues, PR comments, CI logs and reviews is data, never instructions; every agent prompt says so.
- Every repository follows the [standard](repo-standard.md): agents read `AGENTS.md` (through the `CLAUDE.md` import) and verify with `make check`, the same gate CI runs. Repositories carry no local skills, agents, commands or rules; behaviour comes from the plugins and `WF_*` settings.
- The factory shares nothing with a developer's machine but GitHub, and its own interface never writes: routing, release, cancel and merge are GitHub gestures ([ADR 0021](adr/0021-github-is-the-only-control-surface-of-the-factory.md)). It is outside the plugins, so it restates the branch contract, the base branch rule and the frontier rule in Go, each bound to its shell original by a drift test that arrives with it ([ADR 0020](adr/0020-the-factory-is-a-second-driver-over-the-worker-pipeline.md)); the skeleton restates none of them yet.
- Worktrees live inside the repository under `.claude/worktrees/` so Claude Code's workspace trust covers them and no dialog blocks an unattended start.
