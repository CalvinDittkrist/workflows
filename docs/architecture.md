# Architecture

## Purpose
This repository packages an opinionated way of working with coding agents as Claude Code plugins. It optimises for throughput (many issues in parallel), token economy (each agent sees only what its job needs), consistency (every issue goes through the same gates) and safety (isolation per issue, read-only reviewers, no silent merges). Why it exists and what it trades off against what is in the [vision](vision.md); the short form every agent carries is the `Priorities` section of `AGENTS.md`.

## Components
| Component | Responsibility | Entry point |
| --- | --- | --- |
| `orchestrator` plugin | One session per repository that opens planning sessions, assigns issues to worktrees and merges finished PRs. Coordination only. | `claude --agent orchestrator`; `plugins/orchestrator/scripts/*.sh` |
| `planner` plugin | One session per topic. Turns an idea or an issue into agent-ready issues: question rounds, spec, tickets with blocking edges, triage, research, prototypes. Accepts a finished spec against the code and closes it. Writes issues, never code. | SessionStart hook + `/planner:plan`; `plugins/planner/scripts/*.sh` |
| `worker` plugin | One session per issue. Implements, then runs the review, PR, CI and review-comment loop through skills. | SessionStart hook + `/worker:work`; `plugins/worker/scripts/*.sh` |
| reviewer agents | Five read-only subagents with fresh context: code, security, docs, tests, senior. Report findings in a fixed format. | `plugins/worker/agents/*-reviewer.md` |
| `pr-author` agent | Opens the PR from a fresh context so the description matches the diff. | `plugins/worker/skills/pr` (forked skill) |
| `docs-lookup` agent | Read-only subagent that answers one Claude Code question from the current documentation, reached through the worker's pinned `claude-docs.sh`, so the pages never enter the worker's context ([ADR 0030](adr/0030-agents-verify-claude-code-facts-against-the-live-documentation.md)). | `/worker:docs <question>`; `plugins/worker/agents/docs-lookup.md` |
| `spec-checker` agent | Read-only subagent with a fresh context that judges every checkable statement of a spec against the code during an acceptance. | `plugins/planner/agents/spec-checker.md` |
| `factory` service | One service on a host of its own that works the issues routed to it unattended, a peer of the local workflow that owns the delivery pipeline in Go ([ADR 0038](adr/0038-the-local-workflow-and-the-factory-are-peers.md), [ADR 0040](adr/0040-the-factory-owns-the-delivery-lifecycle-in-go.md)), and serves what it did over a read-only HTTP interface with a dashboard built into the binary ([ADR 0033](adr/0033-the-dashboard-is-built-into-the-factory-binary.md)). A Go binary, not a plugin. It claims the head of its line on GitHub, runs a real worker session on it, resumes what it holds after an interruption or a release, runs it again on a review that asks for changes ([ADR 0023](adr/0023-github-is-the-only-control-surface-of-the-factory.md)), checks the shared Claude quota with the host's quota-axi before every run, waiting for the reset when too little is left and resuming a run that ran out of it ([ADR 0037](adr/0037-the-quota-check-waits-below-12-percent-of-the-workers-scope.md)), and gives an issue back when GitHub says the maintainer is done with it — the routing label taken off the issue or the issue closed cancels a run that is going, and every worktree is pushed before it is removed ([ADR 0026](adr/0026-the-factory-never-deletes-work-on-its-own.md)). | `factory/`, `factory/ui/`; `make ui && go -C factory run . -fake -config factory.json`; a host is set up and kept by the [runbook](factory-runbook.md) |
| `repo-standards` plugin | Owns the [repository standard](repo-standard.md): audits a repository against it, applies the approved findings through a backup tag, a cleanup pull request and issues, scaffolds the baseline (`AGENTS.md`, the `CLAUDE.md` import, a `Makefile` with `check`, docs, settings) and checks it, including stray agent configuration; brings the GitHub workspace to the standard with a dry-run-first script. | `/repo-standards:standardize`, `/repo-standards:apply`, `plugins/repo-standards/scripts/check.sh`, `workspace.sh` |
| auditor agents | Six read-only subagents with fresh context, one area each: files, agent configuration, docs, tests and CI, GitHub workspace, security. Return findings in a fixed format. | `plugins/repo-standards/agents/*-auditor.md` |
| Herdr | Terminal workspace manager: one workspace per worktree, agent lifecycle detection, notifications. | `herdr worktree|agent|workspace` |
| GitHub | Issues are the unit of work, PRs the unit of delivery, CI (the job `check` running `make check`) and Codex review the external gates. | `gh` (or `npx gh-axi`) |
| Docker Sandboxes (optional) | Container per worktree for workers that should not touch the host. | `plugins/orchestrator/scripts/sbx-worker.sh` |
| Python suite | Ordinary unittest classes that run the real plugin scripts against the `gh`, `herdr` and `claude` shims in `tests/shims/`. A runner of its own, standard library only, runs the classes on a pool of processes, one per CPU by default (`-j N`), prints what `unittest -v` prints, one class at a time, and takes module or class names to repeat one alone. | `make test`, `tests/run.py` |

## Data flow
0. `/orchestrator:plan <idea | #N>` → `plan.sh` creates `plan/<slug>` (topic or issue in the branch description), a worktree and workspace, starts `claude --agent planner` with `/planner:plan`. The planner grills, writes a `spec` issue, cuts it into `ready-for-agent` sub-issues with native blocking edges and an optional milestone (`issue.sh`), or triages an existing issue into an agent brief. Both stages ask the maintainer per ticket whether it is routed to the factory and recommend against a ticket whose acceptance criteria need Herdr, a screen or a person; nothing is routed that the maintainer did not name, and `issue.sh` refuses a label set that would leave the routing label `factory` without `ready-for-agent` or next to `ready-for-human` ([ADR 0021](adr/0021-routing-is-decided-in-the-planner-and-never-stands-alone.md)). `/planner:finish` removes the worktree; the plan branch never carries commits. `board.sh` then lists the frontier with each issue's milestone: agent-ready issues with no open blocker, no assignee, no worktree and no routing label, so it never offers what the claim refuses, and after it the specs ready for acceptance: open `spec` issues with native sub-issues and none of them open, with the command that opens a planning session on one. Both sections are derived from GitHub on every run and keep no state. `/planner:accept [spec]` runs the acceptance in that planning session: `accept-facts.sh` prints the facts it works from (the spec with its milestone, each ticket with its state and the merged pull requests that closed it, the union of the files those changed, and the deviations accepted in earlier runs), and refuses a worktree that is behind the base branch, because the checker judges the code that worktree carries; one read-only `spec-checker` with a fresh context then judges every checkable statement of the spec against that code and answers `item:` lines, and `accept-report.sh` counts them per section and verdict, refuses a malformed line and names a checkable section the checker left out. The maintainer decides per item that is not met: a gap ticket (a `ready-for-agent` sub-issue on the spec's milestone), an accepted deviation (a comment on the spec that opens with the marker line, which a later run skips) or no finding. Gap tickets keep the spec open until they close and the acceptance has run again; with nothing left open, `accept-close.sh` closes the spec as completed with the closing comment and refuses while a sub-issue is open ([ADR 0015](adr/0015-a-spec-with-tickets-is-closed-by-an-acceptance.md)).
1. `/orchestrator:claim N` → `claim.sh` reads the issue, refuses it unless it carries `ready-for-agent` (the error names its labels and the fix; `--force` is the exception, [ADR 0014](adr/0014-claims-require-ready-for-agent.md)), and refuses it twice more for work that is not this machine's: when it carries the routing label `factory`, because the factory host claims it and opens its pull request from there, and when origin already has a branch of the contract's shape for it, because a claim on the remote is the creation of that branch. Both errors name the label or the branch and the fix, and `--force` is the exception for both; a forced claim over a remote branch adopts it, so the worktree starts from that branch and continues the work pushed to it instead of from the base. It derives `<type>/<N>-<slug>`, creates `<repo>/.claude/worktrees/<branch>` through Herdr (new workspace and pane), starts `claude --agent worker` there with `--settings '{"env":{"WF_MODE":…,"WF_ISSUE":N,"CLAUDE_CODE_DISABLE_BACKGROUND_TASKS":"1"}}'` and the initial prompt `/worker:work`. The background switch makes the session's subagents block and return their report as the tool result, so the worker never spends turns waiting for them ([ADR 0017](adr/0017-worker-subagents-run-in-the-foreground.md)); planning sessions keep background subagents for their research stage. The same settings carry the pane's status line and the two numbers that decide when the session compacts, `autoCompactWindow: 312500` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=80`: the status line script (the orchestrator's) prints issue, mode and context size into the pane and writes the size it read to `<worktree git dir>/worker/context`, the only thing the two plugins share ([ADR 0020](adr/0020-the-pane-measures-the-context-and-the-worktree-carries-the-value.md)), and it is given their product, the compact trigger of 250 000 tokens, to show that size against — the safety net under a session nobody hands over, pinned by the claim rather than left to an undocumented default ([ADR 0031](adr/0031-the-workflow-pins-the-size-at-which-a-worker-session-compacts.md), [ADR 0034](adr/0034-the-compact-trigger-is-raised-through-the-window.md)). The same env block carries the worker knobs the claim was given on its command line (`--env WF_HANDOFF_TOKENS=5000`, only the names the [configuration table](../README.md#configuration) documents for workers, refused before anything is created otherwise): they reach that one session, they win over the repository's settings for their variable, and they hold across every handover of it, because a handover clears the session and does not restart the process.
2. Worker SessionStart hook: parses the issue number from the branch, assigns the issue to the current GitHub user, injects title, body, labels and recent comments as context, marked as untrusted data. When a handoff note is waiting in the worktree it injects that too, with the stage to resume at, and marks the record so no second session start reads it again ([ADR 0029](adr/0029-a-worker-resets-its-context-by-a-handoff-not-by-compaction.md)).
3. `/worker:work` starts its work stage with `base-sync.sh`, which fetches the base and, when the base has commits the branch lacks, merges it with a merge commit, never a rebase, so a branch taken up days after it was made runs its first gate against the base as it is now and every gate and panel record keeps its commit; a branch that has those commits already is left alone, and a conflict stops the worker with `blocked:` and the files, the merge left in the worktree for a person. The factory needs nothing of its own for this, because it runs the same stage. The worker then implements and verifies in its own context, then `/worker:review` launches the reviewer panel in parallel, in one message (fresh contexts, read-only). The worker verifies with `gate.sh run`, which runs the gate once, detached from the call so that it outlasts the Bash tool's ceiling, and waits for it one slice at a time, with `gate.sh wait` for the slices after the first; the detached run records the result for the current head in this worktree's git directory and writes the output to a file beside it, printing it only when the gate failed; `gate.sh print` turns that record into the gate block of a brief and answers for the current head or not at all, so a record from an older commit or from a dirty working tree reads as none instead of as an older value. The gate runs once per review, not per round: round 1 is briefed with the work stage's record, the rounds after it with a pass at an earlier commit and the commits since, and it runs again once before the summary; the stage launches no reviewer without a pass and copies that block into every reviewer's brief, so no reviewer runs the gate itself ([ADR 0019](adr/0019-the-gate-runs-once-per-review-round.md)). The reports arrive as the results of those calls; the worker fixes findings, commits them and ends the round with `panel.sh round`, which records the round's verdicts, fixes and disputes at that commit and answers with the round to run next and the reviewers still on FIX, so the loop runs until every reviewer's last verdict is PASS or until the round limit, which counts recorded rounds and therefore holds across contexts ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). Entering `/worker:review` or `/worker:ci` measures this context first: both skills inject `checkpoint.sh <stage>`, so every entrance meets a checkpoint, from the driver or directly, and the context a handoff started skips exactly that one checkpoint, once, by the session the hook named in the record ([ADR 0032](adr/0032-the-stage-measures-the-context-on-entry-and-a-handoff-grants-one-skip.md)). Between rounds that skill is loaded already and no injection can measure, so `panel.sh round` carries the round's checkpoint in its own answer: a review can hand over after any round, and the fresh context resumes at `review`, where the records say which round it runs and whom it launches. On `handoff: yes` the stage does no work and the answer prints the procedure: a four-section note through `handoff.sh`, which refuses a dirty tree or a missing section, appends base, commits and diffstat, and starts a detached `handoff-resume.sh` that waits for the pane's turn to settle, sends `/clear`, confirms a new agent session id and only then sends `/worker:work` back to the pane, where the hook injects the note and `facts.sh` names the stage to resume at ([ADR 0029](adr/0029-a-worker-resets-its-context-by-a-handoff-not-by-compaction.md)).
4. The review stage ends with `panel.sh record`, which takes only the `disputed:` lines that still stand and derives the panel summary from the round records — the number of rounds, each reviewer's chain of verdicts, the fixes summed by severity — then stores it with the commit it describes and the verdict derived from its `panel:` line, and closes those rounds. It refuses a summary with no round record of this head, so no context can state a panel that did not run, and one at a head the gate has not passed on or over a dirty tree, because that head is the one it would call ready; a head the last round did not read is recorded as a draft that names the commits no reviewer saw. `/worker:pr` forks into `pr-author`, whose brief is the diff context plus `panel.sh print` and `gate.sh print`, so the panel result and the gate result reach the pull request body verbatim without the agent passing them by hand and without the author verifying anything itself; the pull request is never a draft, which no bot reviews: a panel that did not pass is named in the body, and with nothing recorded the body says the panel result is unknown ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). `pr-author` pushes and opens the PR. `/worker:ci` calls `pr-wait.sh`, which reports `conflicts` first when the branch does not merge into its base (GitHub runs no workflow for such a branch, so an empty rollup would read as green), otherwise polls checks and waits for the configured bot reviewers. What it ends on is what a reviewer still asks for, and that is not the unresolved threads alone: a review that states its whole objection in its body leaves no thread behind, so the wait reads the standing requests for changes by the same rule the listing lists them by, and a pull request that carries one is never reported green; `/worker:address-reviews` is shown everything the reviewers still ask for — the summaries of the reviews that ask for changes beside the unresolved threads, because a review whose whole objection is in its body has no thread — fixes them, resolves each thread with a reply and answers each summary with one comment on the pull request (`pr-answer.sh`), which is the only word a reviewer gets about a point that was declined. Every repair round — a fix for failed checks, a merge of the base after a conflict, or a round of thread answers — is counted by `repair.sh round` into a record of this worktree that names the pull request it belongs to, and past `WF_CI_REPAIR_ROUNDS` (default 3) the script refuses, so the limit holds across a handover in the middle of the CI stage instead of being counted in the worker's head. A round somebody asked for by hand is not one of them: a maintainer who read the pull request and requested changes is a new mandate on it rather than another turn of the pipeline's own loop, so `repair.sh reset` starts its count again — on `WF_REVIEW_MANDATE`, the word of the driver that started the session for that review and the name of the review itself, once for it, because a count a session could start again whenever it read itself as asked for, or once per round of the run it was given, would be no bound on that loop at all ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md), [ADR 0032](adr/0032-the-stage-measures-the-context-on-entry-and-a-handoff-grants-one-skip.md)). A `waiting` answer re-runs the wait script and not the skill, so it counts nothing and meets no checkpoint.
5. Manual mode: the worker reports `ready:`, or opens its report with `blocked:` and the question when it stops for a person; the user runs `/orchestrator:merge PR`, which verifies mergeability, removes the workspace and worktree first, then squash-merges and deletes the branch. Yolo mode: `finish.sh` merges and a detached `cleanup-self.sh` removes the worktree; it merges only when the recorded panel says ready, so a run whose panel did not pass ends with the maintainer instead.
6. Standardisation (per repository, user-invoked): `/repo-standards:standardize` in the target repository injects `facts.sh`, runs `workspace.sh` as a dry run, and launches the six auditors in parallel with the facts; the workspace auditor gets the dry-run output instead of exploring GitHub. `report.sh` merges their `finding:` lines into one report per category, separating what the run works through as listed from what `workspace.sh` decides for itself and from what becomes an issue, and `approve.sh` records the answer per category in `<git dir>/standardize/` ([ADR 0016](adr/0016-approval-is-per-category-and-scripts-own-what-they-apply.md)). The report asks about every category the apply phase scaffolds, with findings or without, because rejecting one is what keeps the apply phase out of it ([ADR 0035](adr/0035-every-category-the-apply-phase-scaffolds-is-answerable.md)). Nothing changes in the repository or on GitHub. `/repo-standards:apply` then runs `backup.sh` (the protected tag `pre-standard` and the `skill-candidate` catalogue issue) and `cleanup.sh prepare` (worktree on `chore/standardize`, approved deletions, `scaffold.sh`). The agent fills in what needs judgement, and `cleanup.sh open` opens the cleanup pull request. `issues.sh` turns issue findings into `ready-for-agent` issues. After the merge, `finalize.sh` runs `workspace.sh --apply` when the `workspace` category was approved and the audit found a `configure` line for it, because that line is what approving the category promises; it names where the applied difference deviates from the audited one, posts the snapshot to the catalogue issue and ends with `check.sh` ([ADR 0010](adr/0010-standardisation-audits-read-only-and-backs-up-before-deleting.md)).
7. Factory (unattended, on a host of its own): the service in `factory/` derives one queue of routed issues across its connected repositories, works them one at a time, and starts for each the session a local claim starts, headless and in a process group of its own. Every session is built by one session type (`factory/session.go`): the agent, the prompt, the settings and permission mode, a timeout fixed in Go for its stage and a JSON schema for its result, given with `--json-schema` ([ADR 0039](adr/0039-every-session-reports-through-a-structured-result.md)). It reads the run from the worker's stream — stages from the `Skill` calls, a subagent's events from their `parent_tool_use_id`, the outcome, the pull request and the summary from the structured result on the result line, never from the report text, turns, cost and tokens from the same line — and until that line comes, or when it never does because the factory ended the session on the deadline, a stop or a cancel, from its own count of the assistant lines: one turn per message of the worker itself, the tokens of every message, a subagent's included, taken once per message id, and their cost at the list prices in `factory/cost.go`, a floor the record marks with `"totals": "factory"` and the dashboard as counted, where the result line's are `"worker"` — a tool call a permission check denied from its `permission_denied` line, logged as an error with the reason, and a system line of a subtype the stream reference does not document under that subtype, while only a line that is not a JSON object of the stream is logged as out of the format — and writes one JSON record and one append-only JSONL event log per run into its data directory. The process and the result are read apart: a process that fails is a `failed` run with what it said, a session that ends well without a result line or with a result that does not fit the schema is a `failed` run that says so, a result that reports `blocked` is a `blocked` run whose reason is its summary, and one that reports `complete` with a pull request of the run's repository is a `ready` run. A session that runs past its stage's timeout is ended with its process group and the run fails naming the stage; the run's deadline stays what ends a run with the outcome `timeout`. When a run ends, by itself, on the deadline, on its stage's timeout or on a stop, the whole process group is ended; a process that left the group cannot hold the run open, and the run carries a warning about it ([ADR 0027](adr/0027-the-factorys-isolation-boundary-is-the-host.md)). Its HTTP interface is read-only (`/api/status`, `/api/repositories`, `/api/line`, `/api/runs/{id}`): the factory is steered on GitHub alone ([ADR 0023](adr/0023-github-is-the-only-control-surface-of-the-factory.md)). Under `/` the same binary serves the dashboard those four endpoints feed — the repositories, the line, and the selected run with its stages, its outcome, its cost and its log, the run in the URL so a view can be linked and reloaded. It is a Vite build in `factory/ui` embedded with `//go:embed`, so the host runs one process and no Node ([ADR 0033](adr/0033-the-dashboard-is-built-into-the-factory-binary.md)). It listens before it starts a run and takes the lock of its data directory before it reads one, so a second factory on the host fails before it takes an issue — on the address when the two share one, and on the directory when they do not, because that is what they would race over. The lock is the kernel's and is gone with the process, so a host that was killed starts again. The queue is the routed issues of every connected repository in one line, ordered by the time the routing label was set, oldest first ([ADR 0025](adr/0025-one-queue-one-worker-work-in-progress-first.md)): open, `ready-for-agent`, carrying the routing label, unassigned and unblocked. It is asked from GitHub through the `gh` command on every poll and never written down, so removing a label empties a place in it at the next poll, and a repository that cannot be read leaves the others in the line. A repository the poll could not read is named on the interface with what gh said, because an unreadable repository holds no queue either and would otherwise look exactly like an idle one. The connected repositories are cloned into the data directory on start — one clone per repository, made before the first poll, because a worker branches off it — and the interface says it is connecting while that runs, because a first clone takes minutes and an empty line would be the sight of an idle factory. A clone lands beside its place and is moved in when it is whole, so a clone that was cut off leaves nothing a later start would hand to a worker, and one that fails is reported while the rest still work; a clone is brought up to date by the fetch every claim makes of the whole remote, because nothing ever checks it out again: what the repository says and where its base is are read from the fetched references and not from the working tree the clone was written with. An issue of a repository that has no clone is left standing in the line rather than spent on a run that could only fail, and the log says so once; the same holds a repository whose claim failed without touching anything, because the issue behind it would fail the same way and the next run starts the moment one ends — such a repository waits for the person who starts the factory again ([ADR 0026](adr/0026-the-factory-never-deletes-work-on-its-own.md)). The head of the line is taken by creating that issue's branch, `<type>/<issue>-<slug>`, at that head through the API, which is the one act with exactly one winner ([ADR 0024](adr/0024-a-claim-is-the-creation-of-the-branch-through-the-api.md)): a claimer that meets a branch of the issue records the run as lost and touches nothing else, so two factories and a maintainer may reach for one issue at the same moment. It is any branch of the issue and not only the one it would have created: the number in the branch is what two claimers share when the title was edited between their polls, which is how the local driver reads the remote too (wf_remote_branch_for_issue). Only the factory's own branch is not a foreign claim: one its records name, as below, and one no record names any more because the data directory was lost, which it recognises when the branch carries commits beyond the base, GitHub's activity of the branch names the factory's own login as the last to create or push it, and no pull request of it is open — it then assigns itself, makes the worktree from that branch and continues there. A lost run answers the routing it was started for and no later one: the label set again after it queues the issue like any routed issue. The branch contract and the base branch rule — the explicit setting, then the head the remote points at, then GitHub's default branch — are the orchestrator's shell restated in Go, and the head the remote points at is asked of the remote with every claim, because a clone remembers the one it was written with and no fetch corrects it, and a drift test binds each of them to that original ([ADR 0022](adr/0022-the-factory-is-a-second-driver-over-the-worker-pipeline.md)). The explicit setting is `WF_BASE_BRANCH` as the repository declares it in its own `.claude/settings.json`, which is where a local session is given it and which the factory reads out of the repository's default branch, with the `base` of this host's configuration above it, whatever the repository declares. After a won claim the issue is assigned to the user the host is logged in as and a worktree for the branch is made in the host's clone. Before any session starts, a resumed or a followed-up one as well, in the moment the factory has nothing else running, it updates the `workflows` marketplace and the `worker` plugin with Claude Code's own plugin commands and records the versions of the worker plugin, Claude Code and the factory the run is made with, read after that update: a merged fix to the pipeline reaches an unattended host with its next run, and a run that went wrong can be read back to what made it. It updates neither Claude Code nor itself — a service that replaced its own binary or the runtime under a session it is about to start would be changing itself while it works — and an update that did not work is a warning on the run and never its end, because an older worker is still a worker ([ADR 0036](adr/0036-the-factory-updates-the-worker-plugin-and-nothing-else.md)). In the worktree runs the session a local claim starts, with the worker agent, `/worker:work` as its prompt, the stream of events on its output and the settings object of a local claim without its status line, which nothing renders in print mode: manual mode — the factory never merges what it built — the issue number, the base the branch was cut from, so the pipeline reviews and opens its pull request against that same branch, the planner and the orchestrator switched off, and the compact pin the workflow sets ([ADR 0031](adr/0031-the-workflow-pins-the-size-at-which-a-worker-session-compacts.md), [ADR 0034](adr/0034-the-compact-trigger-is-raised-through-the-window.md)), which is the only safety net a session nobody hands over has. It runs in the auto permission mode, because unattended there is nobody a prompt could ask, and in an environment with no Herdr and no `WF_` variable in it, whatever the factory itself was started with: the settings say what the run is ([ADR 0027](adr/0027-the-factorys-isolation-boundary-is-the-host.md)). The next run starts as soon as the one before it ended, rather than at the next poll. `paused` is read from the configuration on every poll, the one setting that is: a pause written into the file is taken in at the next poll, a run that is going finishes with its own outcome, and after it nothing is claimed, resumed, followed up or let go until the file says otherwise; `-paused` holds whatever the file says, and a file that no longer reads leaves the settings the factory runs with. A stop ends the worker with the factory: the run is recorded as interrupted and its process group dies before the process exits, and a start that meets a record left running marks it interrupted too. The worker of such a run may still be there — a host that killed the factory alone ended nothing — so every run a start finds active is read against the lock its worker holds: the factory opens one file per run, takes it and hands it to the worker's process group, which is the only thing holding it from then on, so a lock the next start cannot take says a process of that recorded group is alive and its number was never handed to anything else. That group is ended, the way a stop ends it and with a kill after the same grace, before the issue is resumed, because two unattended sessions in one worktree is what a restart may not produce. Such a run is resumed once, by itself: the next line the factory derives carries that issue as work it holds, and the session runs again in the worktree of the claim, on the commits that are there, with no branch created and nothing fetched; a worktree that is not on this host — a data directory that was lost, or an issue that was let go and routed again — is made again from the branch on the remote, which is where every worktree this factory removes was pushed to first ([ADR 0026](adr/0026-the-factory-never-deletes-work-on-its-own.md)). A second interruption of the same issue is not, and neither is any other outcome that waits for a person — the branch, the worktree and the assignee stay and the issue is out of the line until somebody takes the assignee off it. That gesture is the release signal: the issue is routed and unassigned again, the factory recognises it from its own records, assigns itself, and resumes it in the same worktree with its one automatic resume given back. Both are read from the run records alone, so a host that was cut off knows on its next start what it holds and what it has already spent, and the release a resumed run answers is recorded with it, so a poll that still shows the issue unassigned queues nothing twice — a resume that ended without taking the issue back has answered it too, because nothing about such an issue changes and the factory would otherwise work the same failing resume for as long as it stands. A held issue is one whose whole claim stands — branch, assignee and worktree — which is what keeps the factory away from a routed issue whose branch another claimer created: that is a foreign claim and is left alone. Only a connected repository is in that line, held work included: disconnecting one takes what it holds out of the line and touches nothing of it. The third signal is a review of what a run left behind. While the factory holds an issue and no run of it is going, the newest pull request its runs reported is read on every poll, and a review that asks for changes on it queues a follow-up run in the worktree of the claim, which starts at the factory's address-reviews stage, so the objection is answered where the work is. It has to be the maintainer's gesture and it has to be new — submitted by somebody who may write to the repository, after the last run of that issue ended, and after the review a follow-up run already stands for — because anybody may review a pull request of a public repository, an objection raised while a run was going is that session's to see, and the poll that queued a follow-up run repeats until its record is written. A plain comment, a review that only commented or was dismissed, an objection the same reviewer later approved away — what one reviewer says is their latest review that states anything, and GitHub leaves the older entry in its list with the state it was submitted with — and a pull request that is closed or merged queue nothing. The review is recorded with the run it queued, as the release is, so one review is one run however many polls read it, and every record says which kind of run it was — first, resumed or follow-up — which is what the dashboard shows of a run that is not the first of its issue. Work the factory holds — resumed and followed up alike — stands before issues nobody has worked yet, ordered among itself by the time of its signal ([ADR 0025](adr/0025-one-queue-one-worker-work-in-progress-first.md)). How the maintainer hears of any of it is GitHub as well ([ADR 0023](adr/0023-github-is-the-only-control-surface-of-the-factory.md)): the logins the configuration names are asked for a review of the pull request when a run ends `ready`, one call per login so that one GitHub refuses or never answers leaves the others asked, and are mentioned in a comment on the issue when it ends `blocked`, `failed`, on the deadline or is interrupted a second time — the outcome, the reason and, where the factory still holds the issue — read from its runs as a whole, so a release resume that failed before it took the issue back is told that an assignee put on and taken off again hands it back — the release gesture in it, with the reason quoted as the text it is, because it carries what a model wrote and the text of an issue can steer that. A run that ends `ready` and names no pull request is commented on the same way: there is nothing to ask a review of, and the issue is held by a factory that is done with it. A lost claim and the interruption the factory resumes itself notify nobody. What an ending owes is written on its record before the call and again after it, so a host cut off in between says it on its next start — a host cut off between GitHub taking the call and that second write says it twice, which is the side of the trade a maintainer can read past, and a paused start marks what it owes and makes none of it, because a pause writes nothing to GitHub; a notification that fails is a warning on the run and changes nothing else, and a factory with no logins configured notifies nobody and says so once when it starts. What the maintainer decides reaches work in progress through the same poll. An issue this factory holds is assigned to this host and so is not in the line, and the poll asks GitHub about each of them on its own: about the issue of the run that is going on every poll, so the gesture that ends it is heard within one, and about an issue that only waits to be cleaned up every tenth, so a host with a dozen pull requests in review does not spend its hour of requests on them. Those readings are one pass with one deadline over it, the run that is going read first: a GitHub that takes a request and answers nothing costs a poll what one read costs and not that for every issue this host holds, and what the pass does not reach the next poll reads. What became of a pull request counts as a decision only when GitHub says that pull request is of the branch this factory holds the issue by — the URL came out of a session's result — so closing another one of the repository ends nothing here. The routing label taken off the issue or the issue closed ends the run that is going; that decision, and the pull request of a run merged or closed, lets an idle issue go ([ADR 0023](adr/0023-github-is-the-only-control-surface-of-the-factory.md)). Letting go is the one path in the factory that removes anything, and it removes nothing that is work ([ADR 0026](adr/0026-the-factory-never-deletes-work-on-its-own.md)): the commits of the worktree are pushed before the worktree and the local branch go, a push that cannot land leaves all of it where it is and says so on the run, the branch on the remote is deleted only when it holds nothing beyond the base it was cut from or when GitHub reports the pull request of it as merged at the commit the branch is at, whatever the merge method, while a pull request closed without a merge keeps it, the assignee is taken off only when no pull request came of the issue, and the issue is marked as let go only once that removal is made, so one GitHub refused is asked for again rather than leaving an issue nobody sees as free; no record and no log is ever touched. It runs in the working loop, because one place at a time may write in the clone, and everything one poll lets go is bounded to a few polls together, so a decision about a dozen issues at once costs the line one deadline and not a dozen. An issue that is routed again after it was let go is taken back on the branch that carries its work, which is what tells that branch from a branch of the same name another claimer cut in the meantime: every claimer spells an issue's branch the same way, and a branch with nothing beyond its base on it is nobody's work to continue. A branch the remote no longer has, and one that carries nothing, is a first run that claims the issue anew; it is a claim of its own, so the pull request of the runs before it decides nothing about it. Fake mode works a canned queue with a scripted worker (`factory scripted-worker`) that needs no tokens, no git and no GitHub, and asks `claude` nothing at all: there is no plugin in such a run to update and no version of one to record. Before a run starts, the factory checks the Claude quota it shares with the maintainer with the host's quota-axi, when the configuration names one: below the minimum of the all-models scope or the worker's model scope nothing starts, the interface says the factory waits for quota and until when, and the check runs again after the reported reset. A check that cannot answer starts the run with a warning ([ADR 0028](adr/0028-the-quota-check-is-a-courtesy-not-a-guard.md)). A session that ends in an error is followed by one more check, and when a scope the worker spends is used up by then the outcome is `quota`: everything the run holds stays, nobody is notified, and the issue is resumed after the reset without spending the one automatic resume of an interruption, once in a row, so a resumed run that runs out again waits for a person ([ADR 0037](adr/0037-the-quota-check-waits-below-12-percent-of-the-workers-scope.md)).
   The pipeline the factory will own ([ADR 0040](adr/0040-the-factory-owns-the-delivery-lifecycle-in-go.md)): the stages implement, gate, review, pr, ci and address-reviews in Go, one fresh session per stage that needs judgement with the factory's own prompts and no plugin update ([ADR 0042](adr/0042-the-factory-carries-its-own-prompts-and-updates-no-plugin.md)), and a change class per connected repository that decides the gate and the reviewers before the pull request while CI stays the full gate ([ADR 0041](adr/0041-a-change-class-decides-the-gate-and-the-reviewers-before-the-pull-request.md)). It takes the stages over one release at a time, from the last to the first, through a temporary stop-after knob of the worker skill ([ADR 0043](adr/0043-the-migration-runs-from-the-last-stage-to-the-first.md)); the structured result is the first step. The ci stage is the first stage the factory runs itself, the address-reviews stage the second and the pr stage the third: the work session stops after `review`, `factory/pr.go` pushes the branch, has a read-only author session write the title and body from the diff, the commits and the issue, appends the recorded gate result and panel summary word for word and opens the pull request against the branch's base, never as a draft, and `factory/ci.go` waits on the pull request, merges the base on a conflict and starts a fix session for a conflicted merge or failed checks, within a repair budget. In the address-reviews stage, review summaries that ask for changes and unresolved threads, each opened by somebody who may write to the repository or by a configured bot reviewer, brief an address-reviews session with the factory's own prompt, which fixes or declines each point and pushes, and the factory posts its replies, resolves the threads it listed and answers the summaries with one comment. A round counts against the same budget, and a follow-up run starts at this stage with a count of its own. Until the last step a run's work session is still the worker skill.
8. Release (manual only): tickets carry a `vX.Y.Z` milestone from `/planner:tickets`, and their spec is attached to it too, so the release waits for its acceptance. `/orchestrator:release vX.Y.Z` → `release.sh` refuses while the milestone is missing or has open issues, or the tag exists. When the default branch is `dev` (`dev` plus `main`) it opens or finds the promotion PR `chore(release): vX.Y.Z` and waits until `merge.sh` merges it with a merge commit, then tags that commit. With `main` alone it tags the head of `main`. It publishes the GitHub release with generated notes and closes the milestone ([ADR 0012](adr/0012-releases-are-manual-and-close-a-milestone.md), [ADR 0013](adr/0013-promotions-merge-with-a-merge-commit-and-releases-tag-it.md)).

## Boundaries and constraints
- Scripts do, agents decide. Everything deterministic (GitHub calls, worktree lifecycle, polling, thread resolution) is a shell script with a stable text output; skills are short prompts around them. This keeps behaviour testable and token use low.
- Plugins are self-contained; they share no code at runtime. `lib.sh` is duplicated deliberately.
- The branch name is the state contract between orchestrator and worker (`<type>/<issue>-<slug>`) or planner (`plan/<slug>`, topic or issue in the git branch description). Everything else is re-derived from git and GitHub, so a crashed session can be resumed or re-claimed; the one exception is a fact of the running pipeline that exists nowhere else, such as the panel summary or the gate result, which a worker script leaves in this worktree's git directory and whose loss degrades the next stage instead of breaking it ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)).
- Reviewers and auditors never edit, and no reviewer runs the gate: it runs once per review in the worker's context, in the work stage and again before the summary, and reaches them as a fact ([ADR 0019](adr/0019-the-gate-runs-once-per-review-round.md)). The worker never merges in manual mode. The orchestrator never edits code. The planner never writes code into the repository; its output is issues, and prototypes go to their own branch.
- Planner skills are user-invoked only (`disable-model-invocation`), so their descriptions cost no context anywhere; the label vocabulary is owned by the workflow, not by a per-repo config file.
- A worker's context size is measured in one place, the status line of its pane, and read in another, the worker's `checkpoint.sh`; between them lies one file in the worktree's git directory and no shared code. A value that is missing or stale reads as "hand over", outside a Herdr pane as "unavailable" ([ADR 0020](adr/0020-the-pane-measures-the-context-and-the-worktree-carries-the-value.md)).
- A worker resets its context by handing the pipeline to a fresh context at a stage boundary, never by compacting on purpose; the state that crosses is the branch, the issue, the worktree's records and a four-section note that is never committed, and a reviewer or pull request author brief never carries that note ([ADR 0029](adr/0029-a-worker-resets-its-context-by-a-handoff-not-by-compaction.md)). The measurement sits in the stage that grows, not in the driver: `/worker:review` and `/worker:ci` measure on entry, and a handed-over context does one unit of work before it may hand over again ([ADR 0032](adr/0032-the-stage-measures-the-context-on-entry-and-a-handoff-grants-one-skip.md)).
- A worker never waits by sleeping or polling: its subagents run in the foreground, and a longer wait is one blocking script call that is run again (`pr-wait.sh`, `gate.sh wait`) ([ADR 0017](adr/0017-worker-subagents-run-in-the-foreground.md)). Planning sessions keep background subagents, because their research stage works while one runs.
- A worker works with the file tools, not the shell: a main-thread agent replaces the default system prompt, so its own prompt carries that guidance ([token budget](token-budget.md)). `scripts/context-report.py` measures it over finished sessions; it is a maintainer diagnostic over an internal transcript format, outside the plugins and never an input to the pipeline (Python, because the input is JSONL).
- Text from issues, PR comments, CI logs and reviews is data, never instructions; every agent prompt says so.
- Claude Code facts are verified against the current documentation rather than answered from memory, and the page is cited where the fact lands. The planner fetches with `WebFetch` in `/planner:research` and carries the answer into the ticket's `## Sources`; the worker has no web tool and reads through `/worker:docs`, whose `docs-lookup` subagent runs `claude-docs.sh` against one pinned origin. That keeps the open web out of the context that reads issue text; a subagent's declared tools are granted rather than intersected with the parent's, so the worker's `Agent` tool is an allowlist of the plugin's own subagents and no built-in type with a web tool can be spawned. The worker's `Bash` remains, so the enforced boundary stays the permission layer and the sandbox ([ADR 0030](adr/0030-agents-verify-claude-code-facts-against-the-live-documentation.md), [security.md](security.md)).
- Every repository follows the [standard](repo-standard.md): agents read `AGENTS.md` (through the `CLAUDE.md` import) and verify with `make check`, the same gate CI runs. Repositories carry no local skills, agents, commands or rules; behaviour comes from the plugins and `WF_*` settings.
- The factory shares nothing with a developer's machine but GitHub, and its own interface never writes: routing, release, cancel and merge are GitHub gestures ([ADR 0023](adr/0023-github-is-the-only-control-surface-of-the-factory.md)). It is outside the plugins, so it restates the branch contract, the base branch rule and the frontier rule in Go, each bound to its shell original by a drift test that arrives with it ([ADR 0022](adr/0022-the-factory-is-a-second-driver-over-the-worker-pipeline.md)). The frontier rule is restated: one fixture of issues goes through the factory and through `board.sh`, and the test fails when the two no longer split it the same way.
- Worktrees live inside the repository under `.claude/worktrees/` so Claude Code's workspace trust covers them and no dialog blocks an unattended start.
