# The local workflow, step by step

Actors: **you** (in the orchestrator pane), the **orchestrator** agent, one **planner** agent per topic, one **worker** agent per issue, the worker's **reviewer panel**, **pr-author**, GitHub **CI**, and **Codex** as external PR reviewer.

| Step | Who | What happens | Done when |
| --- | --- | --- | --- |
| Plan | you → orchestrator | `/orchestrator:plan add offline mode` or `/orchestrator:plan 123`. Script creates branch `plan/<slug>` with the topic or issue in its git branch description, a worktree in `.claude/worktrees/`, a Herdr workspace, and starts the planner with `/planner:plan`. | plan prints workspace, pane, branch |
| Shape | planner + you | `/planner:grill` asks numbered question rounds along the decision tree; facts it looks up itself, decisions are yours. `/planner:research` and `/planner:prototype` settle what talking cannot. Then `/planner:spec` writes one `spec` issue and `/planner:tickets` cuts it into `ready-for-agent` sub-issues with native blocking edges, attached to the milestone you name (or none); the spec joins the same milestone. For an existing issue, `/planner:triage` verifies, grills, posts the agent brief and sets the labels. `/planner:finish` removes the worktree. | issues exist; `/orchestrator:board` shows them in the frontier |
| Claim | you → orchestrator | `/orchestrator:claim 123`. Script refuses an issue that is not open or not `ready-for-agent` (the error names its labels and the fix; `--force` claims it anyway), creates branch `feat/123-slug` and worktree `.claude/worktrees/feat-123-slug` in a new Herdr workspace, starts the worker. | claim prints workspace, pane, branch |
| Context | worker hook | On startup: assign issue to you on GitHub, inject issue text and comments (marked as untrusted data). On resume/compact: one reminder line. | worker knows issue, mode, branch |
| Implement | worker | Reads AGENTS.md, architecture.md, ADRs. Asks once if materially ambiguous. Smallest complete change; bugs reproduced end to end first; docs and ADRs updated; conventional commits, then `gate.sh run`, which runs `make check` and records the result for that commit. | the recorded gate passes for the head |
| Review | worker + panel | `/worker:review`: the gate runs once for the round, in the worker's context, and its recorded result goes into every brief; then five reviewers in parallel, fresh contexts, read-only, none of them running the gate ([ADR 0019](adr/0019-the-gate-runs-once-per-review-round.md)). Worker fixes S1/S2, judges S3, commits, and records the round (`panel.sh round`), which names the next round and re-runs only the reviewers that said FIX. Max `WF_REVIEW_ROUNDS`, counted over the recorded rounds, so the limit holds even when the stage was handed over mid-panel. Disputed findings are kept with their round, not dropped. The stage ends by recording the summary those rounds derive, for the PR stage ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). | all reviewers PASS |
| PR | pr-author (fresh context) | `/worker:pr`: pushes, writes title and body from the diff and issue, uses the PR template, `Closes #123`, and copies the panel summary the review stage recorded (`panel.sh`) into the body verbatim, with the recorded gate result (`gate.sh`) beside it; it verifies nothing itself. A panel that did not pass, or none recorded, opens a draft only you lift ([ADR 0018](adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). | `pr: <url>` |
| CI and external review | worker | `/worker:ci` → `pr-wait.sh` polls checks and waits up to `WF_PR_REVIEW_WAIT` s for a review by `WF_PR_BOT_REVIEWERS` (Codex); on a draft it reports `draft: true` and skips that wait, which no bot answers. `checks-failed` → read failed logs, fix, push. `review-comments` → `/worker:address-reviews` fixes, pushes, replies and resolves each thread. Every repair round is counted into the repair record first (`repair.sh round`), which holds `WF_CI_REPAIR_ROUNDS` across a handover; past it the script refuses and the pipeline reports to the maintainer. | `status: green` |
| Merge (manual) | you → orchestrator | Worker reports `ready:`. `/orchestrator:merge 45` refuses unless checks pass, no threads open, no changes requested, mergeable and CLEAN, and it refuses a draft until you lift it. Then: remove workspace and worktree, squash-merge, delete remote and local branch, fast-forward main. | merge prints `merged:` |
| Accept | planner + you | Once every ticket of a spec is closed, `/orchestrator:board` lists it and `/orchestrator:plan #<spec>` opens a planning session on it. `/planner:accept` prints the facts, lets one read-only `spec-checker` judge every checkable statement of the spec against the code on the base branch, and shows one report. Per item that is not met you choose: a gap ticket, an accepted deviation recorded on the spec, or no finding. Gap tickets keep the spec open until they close and the acceptance has run again. | spec closed as completed with the acceptance comment |
| Release | you → orchestrator | Once every issue in a milestone is closed, `/orchestrator:release v1.2.0`. It refuses while the milestone is missing or has open issues, or the tag exists. With `main` alone it tags the head of `main`. With `dev` plus `main` it opens the promotion PR `chore(release): v1.2.0`, and you merge it with `/orchestrator:merge`, which uses a merge commit and keeps `dev`. Then run the release again: it tags the merge commit, publishes the release with generated notes and closes the milestone. Never automatic. | release prints `status: released` |
| Merge (yolo) | worker | `/orchestrator:yolo-claim` sets `WF_MODE=yolo`; after `green` the worker runs `finish.sh`: squash-merge, Herdr notification, detached cleanup of its own worktree, workspace and branch. It merges only a panel recorded as ready on a pull request that is no draft, so a run whose panel did not pass stops and waits for you. | notification "Merged #45 (yolo)" |

Parallelism: claim as many issues as you like and plan several topics at once; `/orchestrator:board` lists each worktree with agent state (idle, working, blocked), PR, checks and review decision, then the frontier of claimable issues and the specs whose tickets are all closed, which are due for an acceptance. Blocked means the worker is asking something: switch to its pane and answer.

Recovery: everything is derived from the branch name and GitHub. A dead session is restarted with `claude --agent worker` in the worktree (`--continue` keeps its history); pass the flags and the `--settings` object `claim.sh` builds as well, because `--continue` restores the conversation, not the session settings, and without them the worker loses the foreground subagents and carries the other plugins' skills. A stuck worktree is dropped with `/orchestrator:abandon 123` (refuses to delete unpushed work without `--force`).

Per-repository variation: enable a subset of plugins, set `WF_REVIEWERS` and the other `WF_*` variables, and write what an agent must know into `AGENTS.md`. Repository-local skills, agents, commands and rules are not part of the [standard](repo-standard.md); the check fails on them.
