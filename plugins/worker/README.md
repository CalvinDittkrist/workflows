# worker

The main agent has eight tools (Bash, Read, Write, Edit, Grep, Glob, Agent, Skill); everything else stays out of its context. Its `Agent` tool is an allowlist of the plugin's own subagents, so an agent file added here has to be added to the `tools` line of `agents/worker.md` too (tested). The reviewers, the PR author and the documentation lookup run as subagents with read-only tools plus Bash.

One session per issue worktree, started by the orchestrator as `claude --agent worker … "/worker:work"`. Works standalone too: check out a branch named `<type>/<issue>-<slug>`, run `claude --agent worker --settings '{"env":{"CLAUDE_CODE_DISABLE_BACKGROUND_TASKS":"1"}}'`, type `/worker:work`. Without that setting the subagents run in the background and the pipeline waits a turn longer for every panel; `facts.sh` prints which of the two it is as `subagents:` ([ADR 0017](../../docs/adr/0017-worker-subagents-run-in-the-foreground.md)).

Hook: `SessionStart` runs `scripts/session-start.sh`. On startup it assigns the issue to you and injects title, labels, body and recent comments as untrusted task data, every line of them indented, so a heading at the left margin is the hook's own and no text from outside the repository can imitate it. On resume, clear or compact it injects one reminder line — unless a handoff note is waiting, which it injects once with the whole issue and the stage to resume at (see Context below). Silent on other branches and in subagents, except that a test hunt's `hunt/` branch, which names no issue, is given a waiting handoff note.

| Skill | Purpose |
| --- | --- |
| `/worker:work` | pipeline driver: understand → implement → review → pr → ci → finish; the review and the CI stage measure the context as they load, the review stage again with every round it records, and may hand the pipeline over |
| `/worker:review` | `checkpoint.sh review` on entry and `panel.sh rounds` for the round to run, then the recorded gate result in every brief (`gate.sh`, run in the work stage and once more before the summary, not per round), reviewer panel in parallel (`WF_REVIEWERS`), fix, `panel.sh round`, re-review with the reviewers still on FIX (`WF_REVIEW_ROUNDS`, counted over the recorded rounds); no reviewer runs the gate ([ADR 0019](../../docs/adr/0019-the-gate-runs-once-per-review-round.md)) |
| `/worker:pr` | forked into `pr-author`: push and open the PR from a fresh context, with the recorded panel summary (`panel.sh`) and gate result (`gate.sh`) in the body; never a draft, which no bot reviews: a panel that did not pass is named in the body |
| `/worker:ci` | `checkpoint.sh ci` and `repair.sh print` on entry, then `pr-wait.sh`: checks + bot review wait (for the bot's one review of the pull request, on whichever commit it came, so a repair push waits for no second one), returns `conflicts` (the branch does not merge into its base, reported before anything is waited for, because GitHub runs no workflow for such a branch and an empty rollup would read as green), `checks-failed`, `review-comments`, `green` or `waiting`; every repair round is counted with `repair.sh round` first |
| `/worker:docs` | `claude-docs.sh` in a read-only `docs-lookup` subagent: one Claude Code question answered from the current documentation, pinned to `code.claude.com`, so the pages never enter the worker's context ([ADR 0030](../../docs/adr/0030-agents-verify-claude-code-facts-against-the-live-documentation.md)) |
| `/worker:hunt-tests` | driver of a test hunt, started by `/orchestrator:hunt-tests` on a `hunt/` branch: `hunt.sh round` for the shares, one read-only `test-hunter` per share (at most five per message), `hunt.sh triage` per reply, shares of at most 1500 lines, `high` candidates removed and `medium` ones checked by the worker, one commit and `hunt.sh removed` per removed test, up to three rounds while a round finds something new; then the gate, `/worker:review`, `/worker:pr`, `/worker:ci` and the manual finish. The hunt record (`hunt.sh print`) stands in for the issue in every brief; a hunt that removed nothing opens no pull request ([ADR 0045](../../docs/adr/0045-a-test-hunt-runs-on-a-branch-without-an-issue.md), [ADR 0046](../../docs/adr/0046-a-test-is-removed-at-high-confidence-without-approval-before-the-pull-request.md), [ADR 0047](../../docs/adr/0047-a-test-hunt-reads-its-shares-whole-and-hunts-while-it-finds-something.md)) |
| `/worker:address-reviews` | `pr-threads.sh` + `pr-resolve.sh`: fix or decline each thread, reply, resolve |

Agents: `worker` (main thread, opus); the read-only subagents `code-reviewer`, `test-reviewer`, `pr-author` (sonnet), `docs-reviewer` (sonnet, no CLAUDE.md), `docs-lookup` (sonnet, no CLAUDE.md), `test-hunter` (opus, `Read`, `Grep` and `Glob` only, no shell), `security-reviewer` and `senior-reviewer` (inherit the worker model).

Documentation: `scripts/claude-docs.sh` is the worker's pinned way to the Claude Code documentation (not a network boundary: the worker keeps `Bash`, `gh` and `git`). Without an argument it prints the index of the Claude Code documentation, with a page slug (lowercase letters, digits and hyphens, nested with a slash) that page; it builds the URL from a hard-coded origin, speaks https only and prints nothing when the answer came from elsewhere. `WF_DOCS_TIMEOUT` (default 30 s) is the request timeout.

Context: the status line of the pane writes this session's context size into the worktree, and `scripts/checkpoint.sh` reads it, printing `context_tokens`, `threshold` and `handoff: yes | no | unavailable`. `/worker:review` and `/worker:ci` inject `checkpoint.sh <stage>` as they load, so every entrance into those stages is measured whatever the context came from, and a `handoff: yes` prints the hand-over procedure with it; the context a handoff started skips its own stage's checkpoint once, bound to the session the SessionStart hook gave the note to ([ADR 0032](../../docs/adr/0032-the-stage-measures-the-context-on-entry-and-a-handoff-grants-one-skip.md)). Inside the review stage the skill is loaded already and no injection can measure, so `panel.sh round` runs that same checkpoint and prints it with the round it recorded: a review can be handed over after any round, and the fresh context continues at the round the records name ([ADR 0018](../../docs/adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)). Run without a stage the script only reports. `WF_HANDOFF_TOKENS` (default 100000) is the threshold, `WF_CONTEXT_MAX_AGE` (default 900 s) the age past which a recorded size says nothing about this turn and the answer is `yes`. Outside a Herdr pane nothing measures the context and the answer is `unavailable`. Keep the threshold low enough that it plus one review round stays under the compact trigger of 250 000 the claim pins for the session — an upper bound, so leave room under it — or the safety net fires before the handoff does; a review round adds 38k in the median, and it runs after the checkpoint that let it start ([ADR 0031](../../docs/adr/0031-the-workflow-pins-the-size-at-which-a-worker-session-compacts.md), [ADR 0034](../../docs/adr/0034-the-compact-trigger-is-raised-through-the-window.md), [ADR 0032](../../docs/adr/0032-the-stage-measures-the-context-on-entry-and-a-handoff-grants-one-skip.md), [ADR 0020](../../docs/adr/0020-the-pane-measures-the-context-and-the-worktree-carries-the-value.md)).

Handoff: on `handoff: yes` the stage runs none of its own work and the pipeline continues in a fresh context in the same pane ([ADR 0029](../../docs/adr/0029-a-worker-resets-its-context-by-a-handoff-not-by-compaction.md)); the checkpoint prints the procedure with its answer, so a context that entered the stage without the driver's text finds it too. `scripts/handoff.sh <review|ci>` takes a note on stdin with four sections (`## decisions`, `## rejected`, `## verified`, `## open`), refuses a dirty working tree or a missing section, appends base, commits and diffstat, and writes it to `<worktree git dir>/worker/handoff` — outside the tree, never committed, never part of a reviewer or pull request brief. It then starts `scripts/handoff-resume.sh` detached: that waits for the pane's agent to settle, sends `/clear` into the session that asked for the handover and no other, and only when that session's turn has ended — the pane's state is read immediately before every keystroke, including the retry and the driver command, because a pane that waits on a permission dialog or is still working is never typed into and the maintainer is notified instead — and sends `/worker:work` only once the pane reports a new agent session id and the record is marked, the two signals that a fresh context exists and that it has the note; otherwise it clears a second time — asking the pane's state again first — and raises a Herdr notification, leaving the note for the maintainer. A note another session has taken in the meantime — the record is marked as the hook injects it — ends the handover with a notification instead of a second `/clear`. The fresh session's hook injects issue and note — never back into the session named in the record, which is the one that wrote it, and never a note it could not first mark as injected — and records that session as `injected_session:`, which is what lets exactly that context pass its stage's checkpoint once; `facts.sh` prints `resume_stage:`, and the driver starts there. The record stays in the worktree afterwards, so a `/worker:work` typed in that worktree later starts at the stage of the last handover again; the note names its commit, and a stage re-run at a boundary is the cost of reading it late. `WF_HANDOFF_SESSION_MS` (default 60000) is how long a fresh session may take to appear and `WF_HANDOFF_POLL_SECONDS` (default 1) how often the pane is asked; a value that is not a number falls back to the default, because a detached process has nobody to report an error to.

Repair rounds: the CI stage may hand over between two of them, and a fresh context would count from zero, so the count is a record and not a number in the worker's head. `scripts/repair.sh round` counts one repair round — a fix for failed checks, a merge of the base after a conflict, or a round of `/worker:address-reviews` — into `<worktree git dir>/worker/repair` and prints how many the pull request has had and how many it may have; past `WF_CI_REPAIR_ROUNDS` (default 3) it refuses with the `error:` line that says the pipeline stops here and reports to the maintainer, which is where the driver stops. The record names the pull request it counts for, so a second pull request of this branch starts at one again. `repair.sh print` is the same reading without counting, injected by `/worker:ci` so a context started by a handoff learns the count from the record rather than from the note. A `waiting` answer runs `pr-wait.sh` again and not the skill, so it is neither a repair round nor an entrance into the stage: it counts nothing and meets no checkpoint.

Yolo mode (`WF_MODE=yolo`): `finish.sh` squash-merges after `green`, notifies through Herdr, and `cleanup-self.sh` removes the worktree, workspace and branch from a detached process. It merges only a panel recorded as ready at the current head, so a run whose panel did not pass, that recorded no summary, or whose branch has moved past the summary — which a resume at the ci stage makes possible, since it skips the review — ends with the maintainer ([ADR 0018](../../docs/adr/0018-worker-stages-hand-facts-over-through-the-worktree-git-dir.md)).
