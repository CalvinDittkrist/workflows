## Problem
What the user runs into, from their side.

## Solution
What changes for them, from their side.

## User stories
1. As a <actor>, I want <capability>, so that <benefit>.
As many as the feature has; cover every actor and every path, including failure paths.

## Decisions
The implementation decisions the interview settled: modules to add or change, their interfaces and contracts, schema and API changes, notable interactions. Interfaces and behaviour, not file paths.

## Testing
What a good test is here (external behaviour, not internals), the seams, which modules get tests, and prior art in the codebase to copy.

## Vocabulary
New or changed terms for `docs/glossary.md`: `term`: one-line definition. Or "none".

## ADRs to write
One line per decision that is hard to reverse and surprising without context. The worker of the first ticket writes them. Or "none".

## Out of scope
What this spec deliberately leaves out.

## Open questions
What is still undecided, if anything. Empty is the goal.

## Sources
Facts from outside the repository this spec relies on, one line each: the URL and the date it was checked. Claude Code facts come from `https://code.claude.com/docs/en/<slug>.md`. Or "none".

## Notes
Prototype links, research findings, anything else the implementer should know.
